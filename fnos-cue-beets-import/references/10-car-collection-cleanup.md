# 车载倒卖合集：识别 + 全量清洗

**场景**：`_media_archive` 里堆着几个 GB 级的「车载U盘合集」——下载来的倒卖资源，
不能直接入库（会污染音乐库），但用户又想要里面的歌。需要**先识别性质**，
再决定「清洗后另存」还是「直接删」。

实测样本（2026-10-02）：`_车载U盘合集_20260930`，**23423 个音频 / 436 GB / 6 个顶层目录**。

## 1. 能不能「清洗后入库」？先算命中率

用户常问「能不能清掉广告、用 beets 修好标签再入库」。**别直接答应，先跑预检**：

```bash
# 临时库 + 不复制 + 不回写（见 04-quality.md Phase 9）
cat > /tmp/probe.yaml << 'EOF'
directory: /tmp/probelib
library: /tmp/probe.db
import:
    copy: no
    write: no
    quiet: yes
    detail: yes
    resume: no
EOF
mkdir -p /tmp/probelib
beet -c /tmp/probe.yaml -v import -q -s -l /tmp/manual.log <样本目录> > /tmp/probe.log 2>&1
```

**实测（200 个抽样，清洗后）**：

| 指标 | 值 |
|---|---|
| `item_imported` | **22（11.1%）** |
| `Skipping` | 177（88.9%） |
| MB 候选数 | 194 个「Found 5 candidates」但距离不够 → 仍 skip |

**结论**：这类合集**清洗后 beets 命中率仅约 11%**，因为大量是抖音热歌 / 网络歌手 /
翻唱 / 改版，MusicBrainz 里没有对应条目。**「清洗 + beets 入库」这条路投入产出比极低。**

> ⚠️ 统计口径坑：beets 的 `-q` 日志里**没有 "Success" 字样**，
> 要数 `item_imported`（或 `import_task_apply`）。grep "Success" 会得到 0，
> 让人误以为全军覆没。另外 **`-s`（singleton）模式才逐曲按 artist+title 查**；
> 直接按目录导入会把目录当专辑、且若 `TALB` 为空会 `Evaluating 0 candidates`。

## 2. 文件名解析规则（以文件名为准）

这批文件的标签**基本不可信**（广告覆盖 `TIT2`/`TPE1`、`TPE1` 张冠李戴、
GBK 乱码），**唯一可信的是文件名**。实测命名形态四种：

```
455逃跑计划 - 夜空中最亮的星 - 10倍音质.mp3     ← 数字紧贴中文的轨号
004.Olly Murs - That Girl.mp3               ← 英文，点号分轨号
1787.别说我的眼泪你无所谓 子路.mp3              ← 「歌名 歌手」无分隔符
003.沙漠骆驼 - 展展与罗罗.mp3                    ← 「歌名 - 歌手」顺序颠倒
035_Wiz-Khalifa-See-You-Again【不改音响提升…】.mp3  ← 下划线代替空格 + 营销后缀
```

**解析器的四条规则（顺序执行）**：

1. **轨号**：`^\s*(\d{2,4})[\s._\-]*(?=\S)` —— **必须 ≥2 位**，
   否则把 `3D环绕`/`8D音效` 的开头数字当轨号剥掉。
2. **剥广告**：域名 / `小高网分享` / `QQ群号…` / `公众号…`。
3. **剥尾部营销词**（循环，可能叠多个）：`[-–—_]\s*(?:不改音响提升)?(?:\d+倍)?(?:音质|音效)$`
   以及 `无损|高品质|发烧|试音|车载|HQ|SQ|320K`。
   **但保留内容版本词**：`DJ` `Remix` `Live` `翻唱` `伴奏` `环绕` `3D` `版`
   —— 它们描述的是实际内容，剥掉会与普通版混淆。
4. **切分歌手/曲名**：
   - **无中文**（英文/日文名）：只用「 - 」（两侧带空格）切，避免拆坏 `Two-Steps-From-Hell`
   - **有中文**：依次尝试 `\s+-\s+` → `\s+-` → `-\s+` → `-`
   - 切不开（`歌名 歌手` 无分隔符）→ **整串作 title，artist 留空**，交联网解决

**实测结果**：24865 个文件里 **8532 个（36%）** 切不出歌手，必须靠联网查。

**歌手字段里的 `_` 要换成 `&`**（`音决_秦文音` → `音决&秦文音`）。

## 3. 网易云批量查询：命中判定要三道闸

```python
url = ('https://music.163.com/api/cloudsearch/pc?s=%s&type=1'
       '&offset=0&total=true&limit=10')
H = {'Referer': 'http://music.163.com', 'User-Agent': 'Mozilla/5.0',
     'Cookie': 'os=pc; appver=2.9.7'}
```

**返回对象用 `ar`（艺人）和 `al`（专辑）字段**，不是 `artists`/`album`。

三道判据（缺一不可）：

1. **曲名归一化相等**：去括号内容 + 去标点空格 + `zhconv` 转简
2. **歌手包含**：`norm(artist)` 与候选艺人互为包含关系
3. **时长差 ≤ 8 秒**：本地 `mutagen` 读的时长 vs 接口 `dt`（毫秒）
   —— **这道闸门最关键**，实测挡下「同名不同歌」（差 33 秒 / 180 秒）
   和「伴奏版」（`微光` vs `微光 (伴奏)`）

**第四道兜底 —— 子串匹配**：网易云常把原版挤掉，只剩
`展展与罗罗-沙漠骆驼（D.Fly remix）` 这种串。此时用
「`norm(title)` 是 `norm(候选名)` 的子串 **且** 时长差 ≤ 5 秒」收纳，并用 `loose` 标记。

**反向再查一次**：文件名常是「歌名 - 歌手」，正向查不到时交换再查。
成本 +37%，接受。

**限速 1.5 秒/次**（技能 02 实测：快请求会整批返回空）。23407 首 ≈ 13 小时。

**断点续跑**：`/tmp/a3/ne_cache.json`，每 50 条落盘；重跑自动跳过已缓存的。

**实测命中率 62.5%**（40 首样本）。未命中的全是翻唱/网络歌手/Live 版，
**网易云本身就没有**——这是数据源上限，不是脚本问题。

## 4. 流派只能用 iTunes（澄清一个常见误解）

用户可能说「流派用网易云 + 笑匠」，但**这三个都拿不到流派**，实测：

| 源 | 实测结果 |
|---|---|
| 网易云 `cloudsearch/pc` 曲目对象 | **无 genre 字段**（`entertainmentTags` 为 None） |
| 网易云 `/api/album/{id}` | 有 `tags` 字段，但**返回空字符串** |
| 笑匠 `xiaojiangclub.com` | **纯歌词库**（歌词 + 歌词解读），无流派 |

→ **流派必须走 iTunes Search API**，用法见 `03-cleanup.md` 的 **24.13 / Phase 25**
（免 key、国内直连、按 artist 查、`country=us`、3.3s 间隔、曲名交集校验防误配）。

**笑匠的正确用途是歌词**：`/lyrics/{网易云 song_id}.html`，
id 就是网易云 song id，**不需要搜索**，只能补「网易云搜到但无词」的那批（见 `08-lyrics.md` 2.3）。

## 5. 后台任务：用 setsid，不要用 nohup

**坑**：`nohup python3 x.py &` 经 ssh-mcp-server 起不来 —— 会话结束时进程被回收，
日志和输出文件根本不生成（实测踩过）。**必须 `setsid`**：

```bash
cd /tmp/a3 && setsid nohup python3 -u b4_ne_fetch.py > /tmp/a3/b4.log 2>&1 < /dev/null &
sleep 8
ps -ef | grep '[b]4_ne_fetch'          # TTY 列显示 ? 才算真脱离
```

- 加 `-u` 让 stdout 不缓冲，日志能实时看到
- 脚本必须**每 N 条落盘缓存**，否则中断全丢
- 用 `grep '[b]4'` 方括号技巧，避免匹配到 grep 自身（技能坑 51）

## 7. 实测补充：两个查询各自的上限（2026-10-02，23407 首）

### 7.1 网易云：整体命中率约 **35%**，且「反向查询」无效

- 前 390 条样本命中 56%，但样本放大到 2000+ 后**回落到 35%** —— 别拿小样本外推。
- **反向查询（交换 artist/title 再查一次）实测 0 命中**，却让单条耗时 +37%。
  「歌名 - 歌手」颠倒的情况，靠 `search()` 内的「**子串匹配 + 时长 ≤5s**」那一层就能兜住。
- 未命中主因：`no_match`（网易云没这条）远多于 `dur_mismatch`。
  **这批翻唱/网络歌手/Live 版，网易云本身就不收录** —— 是数据源上限，不是脚本问题。
- 速度：限速 1.5s + 单次请求 ≈ **0.54 条/秒**，23407 条 ≈ 11 小时。

### 7.2 iTunes：覆盖率只有约 **10%**，且判据必须改

技能 24.13 的「曲名交集 ≥ 3 才可信」**对车载合集不适用** ——
这批歌手单人在库曲目常常只有 1~2 首，交集永远到不了 3。**正确判据**：

1. **闸门一（主力）：`norm(artistName) == norm(查询歌手)`** —— 接口返回的艺人名必须精确对上，
   这是防同名误配最有效的一道；
2. **闸门二：曲名交集 ≥ 1**（闸门一已严格，这里放宽）；
3. 再按 `primaryGenreName` 的**众数**定流派。

**`GENRE_MAP` 必须配全**，否则会「命中却写不出流派」。实测漏掉过的键：
`k-pop` `j-pop` `t-pop` `mandarin` `tv soundtrack` `traditional pop` `classical crossover`
`instrumental` `vocal` `karaoke` `lullaby` `dubstep` `remix`。
（`k-pop` 尤其常见，BLACKPINK/BIGBANG 全中招。）

**两个工程细节**：
- 扫 23000 个文件读标签要 **5 分钟以上**，务必把「歌手 → 曲名集合」索引缓存到
  `/tmp/a3/itunes_amap.json`，否则每次试点都白扫一遍。
- 歌手名要先剥资源站前缀：`(宝藏音乐).杨多` → `杨多`，实测占 3.5%。
  另把「音乐/歌单/合集/精选/千万/全球/车载/试听」这类词命中且长度 ≤12 的当容器名排除。

### 7.3 阶段 1 遗留的两类脏数据（留到写入阶段统一处理）

- **约 36% 没有 artist**：文件名是「歌名 歌手」无分隔符（`1787.别说我的眼泪你无所谓 子路.mp3`），
  本地规则无解，靠网易云命中后回填。
- **约 3.5% 的 artist 带资源站括号前缀**：`(宝藏音乐).XXX`。
  **不要在查询任务运行期间改文件标签**（会和正在读标签的查询进程竞态），
  统一放到最后一次写入时清理。

## 8. 内容质量筛选：「只留正版原唱」

清洗完之后，用户往往还要一句「把翻唱、网络歌手、DJ/环绕改版都删掉，只留正版原唱」。
**这是语义判断，规则只能覆盖高置信的那部分，必须分级 + 让用户勾选。**

### 8.1 分级规则（三次迭代才收敛，两个反直觉点）

**反直觉点①：营销话术 ≠ 内容被改。**
`不改音响提升数倍音质`、`10倍音质`、`高品质`、`无损` 这些是**卖家话术**，
不代表内容真被处理过。实测把它们当改版标记，会误伤
`32G.../03经典怀旧金曲-不改音响提升数倍音质` 这种目录 ——
抽样确认里面是 `4 IN LOVE - 一千零一个愿望`、`SHE - 恋人未满`、`万芳 - 新不了情`，**都是正版原唱**。
→ **营销词一律降为「疑似」，不参与「明确删」的判断。**

**反直觉点②：「抖音热门」≠ 网络歌手。**
正版歌在抖音火过也叫「热门」。只有 `抖音**网红**歌曲` 才是网络歌手聚集地。
→ **判据用「网红」，不要用「抖音」。**

**最终分级**：

```python
# L1 明确改版/非正规 → 建议删
L1 = r'DJ|串烧|环绕|魔音|全景音效|工体嗨曲|电音夜店|双声道|喊麦|慢摇|' \
     r'抖音网红|抖友|网络流行|网络情歌|翻唱|发烧HIFI|发烧人声|发烧碟|' \
     r'(?<![0-9])[3-8]D(?!\w)'
# L2 疑似（营销话术/体裁标签）→ 列出让用户定夺
L2 = r'抖音|网络|发烧|HIFI|不改音响|音质提升|[0-9]+倍音质|重低音|硬曲|' \
     r'节奏控|舞曲|情歌|轻音乐|综艺|精选'
```

> `[3-8]D` 要加**前后边界**，否则会命中 `3Days`、`8Dio` 这类；`(?<![0-9])` 防止 `1080D`。

实测分布（23423 个）：L1 **10511（44.9%）** / L2 **7139（30.5%）** / L3 **5773（24.6%）**。

### 8.2 「网易云是否命中」**不能**用来判正版

实测 L1/L2/L3 三档的网易云命中率分别是 **18.2% / 18.4% / 18.3%** —— **完全无区分度**。
改版内容同样会被正规平台收录，所以「能在网易云搜到」证明不了「是正版原唱」。
**别用这个信号做筛除依据。**

### 8.3 执行要点

- **分级统计 → 用 AskUserQuestion 让用户多选**（每个选项给出「目录名 + 数量」），
  比让用户看一长串目录名有效得多。
- 用户**没勾选**的类别必须**显式排除**。本批 `车载无损环绕音效音乐合集`（3254 个）
  名字里带「环绕」会被 L1 正则命中，但用户明确不要删 →
  脚本里加 `EXCLUDE = ('车载无损环绕音效音乐合集',)` 白名单优先于黑名单。
- 删前**落盘完整清单**（`path/size/mtime` → `_db_backups_archive/car_purged-<ts>.json`），
  删后清空目录（`os.rmdir` 只删空目录）。
- 实测：10320 个 / 303.68 GB，删除 + 清目录约 1 分钟，零失败。

## 9. 流派：不确定就留空，**别用「艺人级」兜底**

iTunes 是**按艺人**查的（`term=<artist>`，见 24.13）。若拿它的结果给该艺人的
**所有**曲目套同一个流派，等于假设「一个艺人只有一种流派」——
周杰伦既有流行也有中国风，这条假设不成立。**用户明确否掉了这条兜底。**

**正确的流派来源优先级**：

1. **文件自带 `genre`** → 原样保留（实测 1086 个）
2. **关键词规则**（只认「体裁词」本身）→ 写
3. 其余 → **留空**

**规则表**（`RULES`，越具体越靠前）：

```python
('儿歌',   r'儿歌|童谣|宝宝|摇篮曲|lullaby'),
('戏曲',   r'戏曲|京剧|越剧|黄梅|豫剧|评剧|粤剧|昆曲|川剧|秦腔'),
('古典',   r'古典|交响|钢琴|小提琴|大提琴|协奏曲|奏鸣曲|圆舞曲|classical|古筝|二胡|琵琶'),
('原声',   r'轻音乐|纯音乐|器乐|影视原声|ost|soundtrack|配乐'),
('爵士',   r'爵士|jazz|蓝调|blues'),
('民歌',   r'民歌|山歌|牧歌'),
('民谣',   r'民谣|folk'),
('摇滚',   r'摇滚|rock|朋克|金属'),
('舞曲',   r'舞曲|电音|dj|慢摇|串烧|嗨曲|remix|disco'),
('有声读物', r'有声|评书|相声|朗诵|广播剧'),
('世界音乐', r'世界音乐|world'),
('流行',   r'流行'),
```

**两个必须剔除的类别**（它们不是流派）：

| 类别 | 例子 | 为什么不算 |
|---|---|---|
| 语言 / 地区 | `粤语` `闽南` `国语` `港台` `华语` `欧美` `90后` `80后` | 描述语种或受众，不是体裁 |
| 营销 / 歌单词 | `金曲` `成名曲` `经典老歌` `怀旧` `歌单` `精选` | 描述合集属性，不是体裁 |

实测影响：把这两类剔掉后，规则推断从 7965 → **3654**，留空从 3178 → **8340**。
**看起来覆盖率腰斩，但留下的都是站得住的判断** —— 这比填满 76% 但大半是瞎猜要好。

最终覆盖 **4740 / 13089 = 36.2%**：流行 2670 / 舞曲 511 / 原声 247 / 民谣 120 /
古典 61 / 民歌 17 / 儿歌 16 / 戏曲 6 / 世界音乐 3 / 有声读物 2 / 摇滚 1。

## 10. 终校验与流派二次清洗（必做）

### 10.1 只写「空流派」是不够的——原有脏值必须清

第一版写入逻辑是 `if cur: continue`（原有非空的跳过）。**这会把源文件自带的脏 genre 原样留下**。
实测洗完之后，genre 字段里仍有 **1086 个**污染值：

| 类型 | 例子 | 个数 |
|---|---|---|
| 目录名被当流派 | `09.怀旧珍藏版(百听不厌)` / `10.欧美节奏控(清爽唤醒活力)` | 623 |
| 广告 / 上传者 | `晓贝音乐Q/微：171121899` / `车载cd 微信c47383838` / `习习上传qq335020326` | 159 |
| GBK 乱码 | `Î´Öª`(=未知) / `ÁúÏçÊÕ²Ø` / `¡¾www.51ctzs.com¡¿` | 6 |
| 无映射的英文 | `Other` / `Abstract` | 21 |
| 有效英文流派 | `Blues` 204 / `Pop` 51 / `House` 系 20 / `Disco` 1 | 277 |

**处置必须三分支，不是二分**：

```
白名单（自己写的中文流派）      → 保留
英文流派且映射确定              → 译成中文（Blues→蓝调、House 系→舞曲…）
其余（广告/乱码/编号开头/过泛）  → 清空
```

判「该清」的信号，按可靠性排序：`GBK 乱码正则` > `广告关键词` > `^\d{1,3}[.、-] 编号开头`。
**清空比留脏值好**：播放器/App 拿到 `晓贝音乐Q/微：171121899` 当流派，比留空糟糕得多。

清洗后 3931 / 13103 = **30.0%**（比清洗前的 36.2% 低——降的是脏值，不是有效值）。

### 10.2 假 FLAC / 假 MP3：必须用 `file` + `mutagen` 双验

`mutagen` 抛 `FLACNoHeaderError` / `HeaderNotFoundError` 的不一定是「损坏」，
实测有两类完全不同的东西：

| 现象 | 真相 | 判据 |
|---|---|---|
| `data`，头部 32 字节全 `00`，尾部有数据 | **真损坏**（零填充），不可救 | `od -A n -t x1 -N 32` 全是 `00` |
| `file` 报 `RIFF ... WAVE` | **MP3 改名**，实为 WAV | 读魔数 |
| ID3 头正常但 mutagen 报 can't sync | 套壳 / 数据段损坏 | — |

正常 FLAC 头是 `66 4c 61 43`（`fLaC`）。
**扫描时不要只看扩展名**：13103 个音频里混着 7 个假 flac、1 个假 mp3、1 个套壳 mp3。

### 10.3 `beets.db` 的 `path` 是 BLOB，SQL `LIKE` 判中文会骗你

```python
# 错：对 BLOB 用中文 LIKE，永远匹配不上
con.execute("select count(*) from items where path like 'Music/%'")   # 返回 0
con.execute("select count(*) from items where path like '%车载清洗版%'")  # 返回 0

# 对：全部取出来在 Python 里解码再比
rows = [x[0].decode('utf-8','replace') if isinstance(x[0],(bytes,bytearray)) else str(x[0])
        for x in con.execute('select path from items')]
n = sum(1 for p in rows if '/车载清洗版/' in p)
```

实测：`path like '/%'` 只返回 414（BLOB 的 LIKE 是字节比较，行为不可预期），
解码后统计才得到正确结果（13984 条全部是 `/vol2/1000/电影音乐/Music/...` 绝对路径）。
**任何「这个目录入库没有」的判断都必须走解码路径。**

### 10.4 别忘了统计非音频占位

音频体积只是一部分。实测同目录下还有：

| 类型 | 个数 | 体积 | 说明 |
|---|---|---|---|
| `.mp4` | 1337 | **100.58 GB** | MTV 视频 / DSD 天碟视频 |
| `.exe` | 7 | **14.23 GB** | 自解压包，**内含 wav 但从未解压**（等于没用） |
| `.part` | 7 | 0.05 GB | 未下完的残留 |

`du -sh` 与「音频体积求和」差 115 GB 就是这么来的。
**报告体积时两者都要给**，否则用户会以为「删了 300 GB」而实际磁盘没降那么多。
见到 `.exe` 自解压包要特别提示：那批 wav 从未解出来过，要么解压要么删，别当成已有音频。

## 11. 「按艺人删网络歌手」的分层判据（高危，必读）

用「艺人不在库」当判据删网络歌手，**单条判据一定会误伤**。实测从 9602 收到 2687，
四轮收紧，每轮都救回几百到两千个：

| 轮次 | 判据 | 待删 | 救回 |
|---|---|---|---|
| 1 | artist 不在库 | 9602 | — |
| 2 | ＋ 曲名也不在库 | 9193 | 363 |
| 3 | ＋ **繁简归一** ＋ **艺人/曲名颠倒交叉匹配** | 7051 | 2126 |
| 4 | ＋ **网易云收录艺人白名单** | 2687 | 839 |

### 11.1 五类「看似不在库、其实该留」

```
保留 A  有 artist，该 artist 在干净库出现过
保留 C  artist 不在库，但**曲名在库**        ← 艺名写法差异（Mayday vs 五月天）
保留 D  artist/title 解析颠倒，交叉后对上库   ← 文件名是「歌名 - 歌手」被反着切了
保留 E  artist 在**网易云收录过的艺人**里     ← 正规歌手，只是库里没有他的歌
保留 B  无 artist，但曲名在库
删除    以上全不命中
```

判定必须写成**多重 or**，不能层层 else 短路：

```python
if an & lib_artists:                       keep   # 艺人正常
elif tn and tn in lib_titles:              keep   # 曲名在库
elif an & lib_titles or tn in lib_artists: keep   # 解析颠倒，交叉命中
elif an & ne_artists:                      keep   # 网易云收录的正规歌手
else:                                      delete
```

### 11.2 繁简归一不是可选项

库内大量条目是**繁体发行版**（`終結孤單` / `為愛而生` / `五月天`），
清洗版文件名多为简体。不做归一，「曲名在库」这一层几乎全废。

`zhconv` 在飞牛 NAS 上**已装（1.4.3）**，直接 `import zhconv` + `zhconv.convert(s,'zh-cn')`。
归一要放在 `norm()` 里，库侧和文件侧走同一个函数，否则等于没归一。

### 11.3 「无法判断」不能混进「确认不在库」

无 artist 的文件（实测 **3594 个**，占 27%）在 `an & lib_artists` 里必然是空集，
会被静默归入待删。**必须先分流**：

```
有 artist → 走 A/C/D/E 判定
无 artist → 曲名在库保留；曲名也不在库 = "无法判断"，单独一类，默认不动
```

把「无法判断」当成「确认不在库」直接删，是这类操作最大的隐性风险。

### 11.4 删除前必须先出艺人名单让人过目

`by_artist` 汇总（艺人 → 曲目数）导成文本给用户扫一遍，**成本几秒，能拦住整类误伤**。
实测名单一眼就看出问题：`王一博 21`、`杨紫 16`、`中央人民广播电台少年广播合唱团 21`、
`不改音响提升六倍音质 17`（营销词被当艺人）、`一人我饮酒醉 6`（歌名被当艺人）。

长尾很散（1766 位艺人 / 3526 曲目，≥5 首的仅 37 位），所以**只看 Top 25 就够**。

### 11.5 残留：跨语言艺名

白名单兜不住中英对照的艺名：`Mayday`（=五月天）15 首、`王靖雯`（=王菲旧艺名）12 首
仍会被判待删。量小，可接受，**但要在报告里显式列出来**，别当没发生。

## 12. `.exe` 自解压包：p7zip 不够用，要装 unrar

倒卖合集里常见把整批资源压成 **RAR5 自解压 `.exe`**（如「XXX 34张专辑 无损wav 01-05.exe」）。
这类目录**除 exe 外空无一物**，音频全锁在包里，之前所有扫描都看不见它们。

### 12.1 症状：能列目录，却解不出一个字节

```
7z l file.exe        # 正常列出全部文件，Type = Rar5，Encrypted = -
7z x file.exe -oout/ # exit=0，但每个文件都报 ERROR: Unsupported Method
                     # 产出全是 0 字节文件
```

**这是最容易骗过脚本的失败形态**：退出码 0、目录结构完整、文件数正确，
只有 `os.path.getsize()` 才是 0。**统计解压结果时必须查 0 字节文件数**。

根因：实测压缩方法是 **`m3:25`**（标准压缩 + 32MB 字典），
**p7zip 16.02 的 RAR5 解码器不支持**（Debian 12 自带的 p7zip-full 就是 16.02）。

### 12.2 解法：装 unrar，别折腾 p7zip

```bash
sudo apt install -y unrar      # Debian 12 non-free 源，1:6.2.6，仅 141 KB
unrar                          # 验证：UNRAR 6.21 freeware
unrar x -o+ -idq 'file.exe' dest/   # 直接处理 SFX，无需先剥 PE 头
```

实测 22 秒解出 4 张专辑 / 1.8 GB。**unrar 能直接吃 `.exe`**，不用找 offset。

备选：`apt install p7zip-full` 升级到 `16.02+really26.02`（Debian 的版本号命名很怪，
实际是 7-Zip 26.x）也能解；或下载 RARLAB 官方静态包。**unrar 最省事。**

### 12.3 处理流程（wav 原盘 → 带标签的 flac）

```
1) unrar 全量解压到临时区（_<歌手>_tmp/）
2) 查 0 字节文件数（必须为 0）
3) 用 ffprobe 全量验规格（这批实测 450 个全是 pcm_s16le/44100/2ch，标准 CD 抓轨）
4) 目录名解析标签：「张信哲-1989 忘记」→ artist/album/year
   兼容写法：`-` 与 `- `、`张信哲-1998-收藏精选`、尾部 `2CD` 介质标记、
   `(粤语)` 语言标记（剥出来写进 comment）
5) 多碟识别：子目录 `CD1`/`CD2`/`Disc 1`/`Disc 2` → discnumber
6) ffmpeg 转 flac：`-compression_level 5`（level 8 编码耗时翻倍、体积只差约 1%）
   实测 450 首 / 7 分钟
7) 转码后**逐首校验时长**（`|d_src - d_dst| <= 1.5s`），防静默截断
8) mutagen 打标签 + 内嵌封面（cover.jpg > folder.jpg > front.jpg）
9) 删 exe 前先写 manifest（path/size/mtime）
```

### 12.4 精选集重复是正常的，不要去重

实测 34 张专辑 450 首，**唯一曲目只有 281 个**——5 张正规精选集把母专辑曲目重收了一遍
（《爱如潮水》出现在 6 张专辑里），82 个曲目有重复、冗余 169 条。

这是**专辑收藏的完整性**，与「同一首歌存了多个格式」是两回事。
前者是不同专辑各自收录同一作品，后者是同一作品的多份副本。
**误按「同曲去重」处理会把精选集掏空。** 只在报告里说明重复情况即可。

### 12.5 附带的内页资源别丢

这类包通常还带 `cover.jpg` / `back.jpg` / `folder.jpg`、`list.txt`（**GBK 编码**的专辑文案）、
`Booklet/` 内页图、少量 `.doc` 专辑介绍。解压后把图片一起复制到输出目录，
`list.txt` 可用来核对专辑名与发行年份。

## 13. singleton 导入：判重、mp4 剥离、白名单复查

实测把一个 10408 首的清洗版灌进 beets（`beet import -s`）踩了三个坑，
**每一个都会造成不可逆的污染**。导入前必做预检。

### 13.1 导入前必须算唯一键 —— 否则文件互相覆盖

beets 的 singleton 路径模板是 `$albumartist/$title`（`paths.singleton`）。

清洗版这种「多套 U 盘资源堆叠」的目录，**同 (artist,title) 会有多份**：
实测 10408 首里只有 **6233 个唯一键**，2847 组重复、涉及 **7021 个文件**（最多一组 14 份）。

**导入前先算**：

```python
# 把两件事都统计出来，一个都不能少
dup_internal  = (artist,title) 在待导入集合内重复    → 导入时互相覆盖
collide_lib   = (artist,title) 已在库里存在         → beets 判 duplicate 或覆盖现有文件
no_artist     = artist 为空                        → 生成 Music/<曲名> 畸形路径
```

**去重保留规则**（与老张的格式优先级一致）：`FLAC > WAV > APE > 其他按码率`，
质量相同时保留**路径更短**的（通常来自更干净的来源）。

实测：去重删 4161 个 / 36.86 GB。

### 13.2 无 albumartist 必须给兜底，不能交给模板

`$albumartist/$title` 在 albumartist 为空时会产出缺一级的畸形路径。
实测 **3585 个**文件没有 artist。统一写「**未知艺术家**」（或你的 `va_name`）。

注意：**WAV 不支持 `albumartist` 帧**（报 `not a Frame instance`），
这批要用 `mutagen.wave.WAVE` + ID3 帧（`TIT2/TPE1/TPE2`）单独写，
仍有部分读不出的（ID3 chunk 损坏）——先移到 `_pending_fix/` 别硬塞进导入。

### 13.3 `beet import -s` 会吃掉 `.mp4`

**这是最容易被忽略的污染**：beets 把 `.mp4` 识别为 MPEG-4 音频容器，
于是 1326 个 MV 视频被当成音乐入库，title 被解析成 `www.xgw5.com` 这类广告域名，
文件被移动到 `Music/<广告域名>.mp4`。

**导入前先按扩展名过滤**，只保留真正的音频扩展：

```
音频：.mp3 .flac .wav .ape .m4a .aac .ogg .wma .dts .opus
排除：.mp4 .mkv .rmvb .part .tdl .sfv .ini
```

已经导错的修正：库内删 items（级联 `item_attributes`）→ 文件移到 `_mv_videos/` → 清空目录。
**但别把库内原有的 `.tdl`/`.part` 一起删**（实测有「五月天音乐电影」的 `.tdl` 是原有资料），
先按扩展名+路径特征区分「本次导入的」与「原有的」。

### 13.4 白名单会误保护，收尾必须复查艺人字段

用「网易云收录过的艺人」当正规歌手白名单时，会把营销词也保护下来：
实测 `9月热门无损DJ串烧`（45 首）、`不改音响提升六倍音质`（14 首）因此漏网入库。

**收尾查一次 artist 字段的营销特征**：

```python
BAD = re.compile(r'不改音响|音质|[0-9一二三四五六七八九]+倍音质|串烧|环绕|魔音')
BAD_EXACT = {'DJ'}      # 只匹配完全等于 DJ，不能拿 DJ 做子串！
```

**规则必须精确**，否则误伤真艺人：`DJ OKAWARI`、`DJ KAJJIN`、`DJ Drama`、
`Ramin Djawadi`（权游配乐）、`Lofi Fruits Music`、`N Music` 都是真人。
所以 **`DJ` 只能精确匹配、`Music` 绝对不能当关键词**。

title 字段同理别乱清：`QQ爱`、`Don't Stop The Music`、`Angel of Music` 是真歌名。

### 13.5 导入后必查三件事

```
1) 库内总条数 == 导入前 + 本次导入数 − 剥离数
2) select count(*) from items where 路径不存在 → 必须为 0
3) 按扩展名统计 → 确认没有 mp4/part 混入
4) 顺带看 App 日志：FSEvent + persistAudioFileTrack 有无正常触发、error.log 有无新增
```

实测最终：20610 条、失效记录 0、App 实时同步（FSEvent 3907 次、逐曲入库 9947 次）。

### 13.6 清洗版残留的 `.lrc` 可以挂回去

音频被 beets 重命名成 `<track> <title>.ext` 后，原 `.lrc` 就成了孤儿。
按「**去掉轨号前缀后的文件名 == 库内 title**」可以精确匹配挂回：

```python
nb = re.sub(r'^\s*\d+\s*[.\-、]\s*', '', os.path.splitext(os.path.basename(lrc))[0])
if nb in by_title:   # by_title: 库内 title -> item path
    tgt = os.path.splitext(by_title[nb])[0] + '.lrc'
```

实测 2769 个里挂回 **487 个（17.6%）**，其余对应的音频已在前面几轮被删掉。

### 13.7 MV 归档：仓库是 `电影音乐/MV/`，命名规则 `<歌名> - <歌手>.<ext>`

⚠️ **先说位置**：老张的 MV 仓库一直是 **`/vol2/1000/电影音乐/MV/`**——
与 beets 库根 `Music/` **平级**，不是 `Music/MV/`。

**踩过的坑**：用户说「mp4 文件按照规则移动到 music/mv 目录」，我按字面在 beets 库根下
新建了 `Music/MV/`，结果那本来就是个**已存在的资产目录**（888 个文件 / 31 GB 的老 MV 收藏，
命名如 `Bad Boy - 张惠妹.mkv`、`fly away - 梁静茹.mkv`，部分文件属主是 `xunlei-app`）。

**规则**：用户提到一个目录名时，**先在磁盘上 `ls` 确认它是否已存在、里面有什么**，
不要按字面新建同名目录。用户已有的目录往往带着既定的命名规范。

**该仓库的命名规则**：`<歌名> - <歌手>.<ext>`
（`Bad Boy - 张惠妹.mkv`、`I See Us - 周深.mp4`、`黑色午夜 - 张国荣.mkv`）。

**放置策略**：

```
MV/                      ← 根目录只放符合 <歌名> - <歌手> 规则的
MV/_未识别MV/            ← 曲名丢失、无法规范命名的（统一编号）
MV/_其他/                ← part/rmvb 等残片
MV/_整理日志_*/          ← 用户原有的整理日志
```

**App 不扫非音频**：日志明确 `skip non-audio file`，放哪个目录都不会污染音乐库。

**但曲名会在 beets 导入时丢失**：`beet import -s` 用 `$title` 模板重命名，
mp4 的内嵌 `©nam` 为空时 beets 用 `_` 占位（`_.355.mp4`），
**原始文件名（`4089.今生若无遇见 赵真.mp4`）在那一刻就没了**。

补救顺序（下次要提前做）：

```
1) 导入前先落盘「原始路径清单」—— 这是唯一能事后追溯的依据
     find <源目录> -type f > /tmp/orig_paths.txt
2) 或直接跳过 beets，自己按文件名搬到 MV/ 并按规则改名
3) 事后补救只剩「用 MV 音频轨道与音乐库做指纹匹配反推歌名」，成本很高
```

实测 1340 个里只有 **125 个能读到 `©nam`**（都是 `dj <歌名> <歌手>` 格式），
其余 **1212 个只能编号**；且那 125 个里 **120 个是 DJ 版**、去重后只有 **43 个唯一名**。
