## Phase 22 — rmtree 误删事故的**恢复**与防再犯（2026-09-30，37 个文件）

### 22.1 事故链与防再犯

- 事故：`a3_rollback.py` v1 `shutil.rmtree(目标目录)` 删掉了 37 个老库文件。
- **回滚脚本安全规则（已固化）**：
  1. 只删「在 `items` 表里登记过」的文件；非本批文件一律保留；
  2. 目录只在**删空之后**才移除，非空则打印 `[保留]` + 剩余内容；
  3. 空目录清扫**限定在本批目标子树内**，不再全库 `os.walk`；
  4. 绝不 `rm -rf` / `rmtree` 任何目标目录。

### 22.2 恢复流程（`a3_recover2.py`）

```
1. 从事故前备份库 beets.db.bak.<tag> 取回「当前库里没有」的 items 行
2. 在归档区（已转换专辑 / _media_archive / 音乐 / Music）建音频索引：
   (路径, 归一化去编号文件名, 分词集合)
3. 一趟打分 → 取 top12 → 二趟「tag + 文件名分词」复核 → trust
4. trust 的：insert 回 items/albums 行 → 从源 copy 回原路径 → write_id3 重写标签
5. 不 trust 的：写一份《丢失清单》文件，**不要**在库里留空路径记录
```
- 实测 **34/37 自动恢复**；1 个从 MV 音轨 ffmpeg 提 mp3 顶替（已降级，需在清单里注明）；
  2 个全盘无源 → 只能记为数据丢失。
- 归档区索引实测 53313 个音频，建立一次约 1~2 分钟 —— 值得为恢复单跑一次。

### 22.3 恢复后必做

- 库内磁盘缺失 = 0；
- 留一份《丢失清单》（含源路径、降级说明、不可恢复项）放在库根，便于以后审计；

## Phase 26 — 自动化任务**误执行写操作**（2026-10-01 实测）

### 26.1 事故
起了个「每小时汇报重查进度」的 recurring automation（只读）。它的 prompt 里写了：

```
4. 若进程已结束：…并提示下一步 —— 跑 `python3 /tmp/a3/a11_apply.py`（先 dry-run）查看…
末尾：不要执行任何写操作或修改文件，只读取和汇报。
```

**结果：`a11_apply.py --apply` 被真跑了**（`beets.db` 的 mtime 暴露），
库里 5898 条记录被改：清空 3832 / 改值 952 / 填入 1114。

### 26.2 根因
- **prompt 里出现了「脚本名 + 执行动词」的组合** —— 我本意是"告诉你下一步可以跑它"，
  agent 理解成"去执行它"。
- 「不要执行任何写操作」这句**太抽象**，没能覆盖"执行一个叫 apply 的脚本"这种具体行为。

### 26.3 正确写法（automation prompt 的铁律）
```
【只读铁律】你唯一允许执行的命令是下面这一条（以及它的只读变体）：
  <粘贴一条纯只读命令>
禁止：执行任何脚本、任何 --apply 、任何写库/写文件/移动/删除操作、
      执行上面没列出的任何命令。发现任务已结束 → 只汇报状态，不要"帮忙推进"。
```
- **绝不出现**「跑 xxx.py」「执行 xxx」「下一步 xxx --apply」这类句式
- 若要提示后续步骤，写成**描述**而非命令：
  「后续需要人工决定是否执行写库步骤」——不写脚本名，不写命令
- 只读命令也要显式列出**允许的那一条**（白名单比黑名单可靠）

### 26.4 事后定位方法（可复用）
怀疑库被非预期改动时，**用备份库与当前库做差集**，按变更类型分类：

```python
om = {id: genre for ... in sqlite3.connect(BAK)}
nm = {id: genre for ... in sqlite3.connect(DB)}
diff = [(i, om.get(i,''), nm.get(i,'')) for i in set(om)|set(nm) if om.get(i,'') != nm.get(i,'')]
# 分类统计：清空(有→空) / 填入(空→有) / 改值
```
**差异的"形状"直接对应脚本的行为**：本例「清空 3832 + 填入 1114」正是
`new = rec['g'] if hit else ''` 这条逻辑的指纹，一眼锁定是哪个脚本干的。

再配合 `ls --time-style=full-iso beets.db` 看 mtime，就能对上时间点。

### 26.5 处置原则
- **先判定结果是否可接受**，再决定回不回滚。本例结果符合用户既定口径
  （「单曲优先级最高，搜不到留空」），故**不回滚**，但明确告知代价
  （清空里含原本合理的值，如 张学友《夢中的妳》'粤语流行'→空）。
- 立即**删除或暂停**那个 automation，避免反复触发。
- 把「误执行」这件事本身**写进日志和报告**，不隐瞒。

## Phase 27 — 后台「接力」脚本的 `pgrep` 自匹配死循环（2026-10-01 实测）

### 27.1 现象
挂了个接力：等 a14 查询结束后自动跑 a15 生成计划。

```bash
bash -c 'while pgrep -f a14_itunes_lib >/dev/null 2>&1; do sleep 60; done;
         python3 -u /tmp/a3/a15_build_plan.py > /tmp/a3/lib_plan.log 2>&1'
```

a14 早已正常结束（日志写了「查询完成：2751 个文件」），**接力却一直不触发**，
`pgrep -af a14_itunes_lib` 还能匹配到进程。

### 27.2 根因
**`pgrep -f` 匹配完整命令行，而接力自己的 `bash -c` 命令行里就含有 `a14_itunes_lib` 这个字符串**
—— 它匹配到了自己。同理，`ps aux | grep xxx` 也会匹配到 grep 自身
（所以惯例写法是 `grep '[x]xx'`）。

### 27.3 正确写法
```bash
# ✅ 用 PID 文件（最可靠）
bash -c 'while kill -0 "$(cat /tmp/a3/a14.pid)" 2>/dev/null; do sleep 60; done; <后续>'

# ✅ 或者用精确匹配排除自身（-x 全等 / 加方括号技巧）
while pgrep -x python3 >/dev/null && pgrep -af 'python3 -u a14' | grep -qv "$$"; do ...

# ✅ 或者干脆不要接力：查完手动跑（最省心）
```

**教训：任何"等某个后台任务结束"的接力，判活条件都不要用
`pgrep -f <关键子串>`，除非该子串绝对不会出现在接力自身的命令行里；
首选 PID 文件 + `kill -0`。**

### 27.4 排查方法
```bash
pgrep -af <关键字>          # 看究竟匹配到了谁（本案例能看到匹配到的是接力自己）
ps -eo pid,cmd | grep '[p]ython3 -u a14'   # 用方括号排除 grep 自身，确认真进程是否还在
```

### 27.5 处置
- 杀掉假死的接力，**手动执行后续脚本**；
- 事后确认产物（`lib_plan.json`）已生成、内容正确；
- 不要因为"接力没触发"就重跑上游查询（缓存还在，重跑是浪费）。
