# ABAP 需求 → 详细开发文档

## 核心原则

**不要照着需求原文写文档。** 需求原文里的字段名、口径、业务前提经常与代码实际不符。文档的价值在于用**代码证据**把不一致的地方钉死，并把"这个需求能不能落地"的结论前置。

## 步骤

### 1. 先把关联对象全部找齐

不要只看用户指定的那个程序。用 Glob 按程序号/表名在整个工作区搜：

```
Glob  pattern="**/*<程序号>*"
```

经验：一个 SAP 项目的工作区里通常还躺着**需求里提到的上游程序**（配置维护程序、字典 HTML、既有设计文档、项目 memory）。这些是判断需求可行性的关键，缺了就只能靠猜。

优先读：`ZFI_R_<需求提到的程序>/` 下的源码、`dictionary/*.html`、`.workbuddy/memory/MEMORY.md`（项目约定）、以及同级目录里的 `*.md` 设计文档。

### 2. 解析字典 HTML 拿字段元数据

每个字段一个 `<tr class="cell">`，10 个 `<td>`：序号|字段名|位置|键|数据元素|域|类型|长度|小写|域文本。

```python
import re, html
src = open(path, encoding='utf-8', errors='replace').read()
for r in re.findall(r'<tr class="cell">(.*?)</tr>', src, re.S):
    tds = [html.unescape(t).replace('\xa0', '').strip()
           for t in re.findall(r'<td>(.*?)</td>', r, re.S)]
    # tds[1]=字段名 tds[3]=键 tds[4]=数据元素 tds[6]=类型 tds[7]=长度 tds[9]=域文本
```

Python 用托管版本 `C:\Users\garso\.workbuddy\binaries\python\versions\3.13.12\python.exe`。
本环境 Bash 里 `ls`/`wc`/`dirname` 可能不可用，改用 Glob / Read / Grep 工具。

### 3. 用代码证据验证需求原文的字段映射（最重要的一步）

涉及"哪个字段关联哪张表"时，**不要采信需求原文的字段名**，去做三件事：

1. `Grep` 该字段名在目标程序里的**全部出现位置**。若只出现在 ALV 列定义（`m_fieldcat`）而从未参与业务逻辑，说明需求写的是显示列名，不是实际参与 Join 的字段。
2. `Grep` 目标程序里读那张关联表的语句，看 `WITH KEY` / `WHERE` 用的是哪个字段——那才是真正的映射字段。
3. 到配置维护程序里看它的 `resolve_*` / 保存逻辑，确认配置端的取值链路。

同类字段名带后缀（`KUNNR` / `KUNNR_GM` / `KUNNR_GM2` / `KUNNR_ID`）时，中文描述往往一样，更容易串。把证据链（文件:行号）写进文档。

### 3.5 阶梯 / 门槛类匹配：必须问清是「明细级」还是「汇总级」

需求里出现"按某个金额匹配档位/费率/折扣"时，一定要确认匹配用的金额是**当前这条明细自身的金额**，还是**先按某个维度汇总后的金额**。

判断线索：**看门槛的量级**。如果门槛是万元级（配置界面常按"万元"录入，如 `SALES_AMTn`），而业务单据单行金额只有几十元，那么逐行比必然永远落空 —— 这种需求一定是汇总级。**这类错误不会报错，只会让结果静默全为空**，比语法错误难发现得多。

汇总级实现的三步套路（也是性能上唯一合理的做法）：

1. **汇总**：建一个 `HASHED TABLE`，键取汇总维度（如 公司+年月+客户+观麦客户），遍历明细累加金额。用 `READ ... ASSIGNING` + `INSERT` 的读改写，**不要**在大表上用 `COLLECT`（标准表是线性查找，O(n²)）。
2. **匹配**：遍历汇总表逐组匹配，结果按同一键缓存到另一张 `HASHED TABLE`。**同一个组合只算一次**。
3. **套用**：再遍历明细，按键取回匹配结果，逐行算金额。

两个容易踩的位置问题：

- **汇总要放在明细主循环之后**，如果汇总维度里含**主循环中才回填的字段**（如客户号由映射表回填），放前面会全是空值。
- **要放在"备份/落库"之前**，否则备份表带不到计算结果。

最后在交付文档里加一句可自检的口径：**"同一<汇总维度>下的所有明细行，匹配结果应完全相同；出现不同即为缺陷"** —— 这句话让业务和测试都能一眼验证。

### 4. 反查"这个需求能不能配置出来"

需求的兜底/通用逻辑常依赖配置表里的**空值行**（空客户、空公司等）。必须去读配置维护程序的保存校验：

- 有没有 `IF xxx IS INITIAL` → RAISE EXCEPTION？
- 有没有 `SELECT ... FROM 映射表` 后要求 `lines( lt ) = 1`？

只要有，空值行就存不进去，需求里对应的兜底级别**永远匹配不到**。这是最容易漏、也最有价值的发现，必须前置为 P0 阻塞项并给出配套改造范围。

### 5. 复用既有的纯计算方法，不要在循环里调服务方法

配置模块通常会提供两种入口：
- `GET_xxx`：查库 + 权限 + 校验，**逐行调用会产生 N 次数据库往返**；
- `DETERMINE_xxx` / `CALCULATE_xxx`：**纯计算、无数据库访问**，设计意图就是给外部复用。

报表侧的做法：报表开始时**一次性 SELECT** 建 `HASHED TABLE`（键取配置表主键），循环内只做内存查找，判定调纯计算方法。同时在文档里明确禁止循环内 `SELECT`。

### 6. 新字段落位要沿用项目先例

不要一律往主表加字段。先看项目里"同类计算列"放在哪儿：
- 由本程序计算得出的列 → 往往只加在 ALV 结构 + 备份表，主表不动；
- 由接口写入的列 → 才在主表里。

在文档里列出现成先例（哪些列在、哪些列不在），让评审者一眼看出这是惯例而非随意决定。
另外必须提醒：`MOVE-CORRESPONDING` / `SELECT ... INTO CORRESPONDING FIELDS` 按字段名映射，**ALV 结构与备份表的同名字段必须同类型**，否则静默丢数据。

### 6.5 把「原有计算逻辑」整理成设计基准

新增计算逻辑之前，必须先把**目标程序原有的计算逻辑**梳理清楚并写进文档，作为新设计的参考基准。做两件事：

1. **分清「谁写的」**：用 Grep 检索每个金额字段在程序里的全部出现位置。**从未被赋值的字段 = 接口/上游写入的原始值，报表只读**；只有被赋值的才是本程序计算的。这一步能避免把接口字段误当成"报表算出来的"。
2. **按「原始值 → 外部带入 → 本程序计算」三层列表**，逐条给出公式与行号，然后归纳出可沿用的范式。

经验上，这类报表的计算范式通常只有两条：**「单位值 × 数量」型**和**「有加总关系的一组金额用加总推导」型**。新逻辑应显式映射到这两条范式上，并在文档里附一张「原逻辑要素 → 新逻辑做法 → 一致性」的对照表。

好处：**当你发现某个看似"自创"的规则其实正是原逻辑已有的范式时，它就从一个待商榷的提案变成了有依据的设计。** 例如"结算销售额 = 结算不含税 + 结算税额"这种倒挤写法，若原程序里已有 `总成本 = 成本金额 + 量差金额 + 价差金额`，就直接引用它作为依据，而不要写成"为满足凭证平衡而额外采用的处理"。

反之，如果新逻辑确实引入了原有程序没有的范式，必须在文档里单独标注出来并说明必要性。

### 6.6 改完后必做三件自检（都是踩过坑的）

**⓪ 结构类型一律用 `TYPES` 声明**

`TYPES: BEGIN OF ty_x, … END OF ty_x.` 才创建**类型**；`DATA: BEGIN OF ty_x, … END OF ty_x.` 只创建一个叫 `ty_x` 的**结构变量**。两种写法长得一模一样，极易混。写成 `DATA:` 之后再 `TYPE ty_x` 或 `TYPE HASHED TABLE OF ty_x` 就会报「类型 TY_X 未知」。

**新增内表结构时固定按这个顺序写**：先 `TYPES:` 声明类型，再单独 `DATA:` 声明内表和工作区。定稿前扫一遍全文，确认所有 `TYPE … OF ty_*` 引用的名字都出自 `TYPES`。

**① 「引用 × 结构声明」交叉核对**

把计算列接进下游（凭证、汇总结构、接口）时，容易只按"引用点"逐处替换，忘了反向检查"每个被引用的字段，其所属结构是否都已声明"。结果是编译期才报「数据对象 XXX 没有名为 YYY 的组件」。

做法：替换完成后，用脚本扫描全部 `结构变量-新字段` 形式的引用，逐一比对目标 `TYPES` 结构里的字段声明。**同一张表的多个汇总结构往往只加了部分字段，最容易漏。**

**② ABAP 形参传递的类型规则 ≠ 赋值规则**

给方法/函数的**形参**传值时，实参与形参的类型必须**兼容**（同类同型），**不允许 CURR ↔ DEC 这类跨类型**；而普通的 `=` 赋值是可以隐式转换的。

典型翻车点：把 DDIC 的 `CURR` 金额字段直接传给形参为 `DEC` 的方法参数，报「与形式参数类型不兼容」。

正确写法是先落到一个目标类型的变量上再传：

```abap
DATA lv_amt TYPE <目标表>-<目标字段>.   " 与形参同类型
lv_amt = <源字段>.                      " 赋值允许隐式转换
CALL METHOD ... EXPORTING iv_amt = lv_amt.
```

设计阶段就应查清被复用方法的**形参类型**（用 SE24 或源码签名），不要凭"数值字段都差不多"下判断。

**③ 「ALV 列定义字段名 × 输出结构字段」交叉核对**

给 ALV 加列时，`frm_fieldcat` 里的 `fieldname` 是**字符串常量**，编译器不会校验它是否真的存在于输出结构中。写错一个字母（例如把 `HSL_JSSJECJ` 写成 `HSL_JSSECJ`，漏掉一个 `J`）的后果是：

| 环节 | 结果 |
|---|---|
| 语法检查 `Ctrl+F2` | **通过** |
| 激活 `Ctrl+F3` | **正常** |
| 运行报表 | **不报错、不 dump**，只是那一列**不显示或全空白** |

也就是说，**「程序跑通了、ALV 出数了」完全不能证明列是对的**。必须单独做一次核对：解析全部 `m_fieldcat` 的字段名，与输出结构字段做全量比对，并检查列定义内有无重复字段名。

> ⚠️ **核对时必须处理 `INCLUDE STRUCTURE`**：输出结构常以主表打底（如 `ty_show` 开头就是 `INCLUDE STRUCTURE zfit0047`），要从字典里把这些字段一并并入结构字段集 —— 否则 `BUKRS`、`KUNNR` 这类合法字段会被大批误报为"不存在"。

**④ 派生列的差异列要保持加总自洽**

若某列是由其他列**加总推导**出来的（为规避舍入尾差），那么它的"差异列"也会自动满足同样的加总关系。这个关系应作为**测试要点**写进文档，让测试能一眼判断"是程序错还是源数据不满足恒等式"。例如 `结算销售额 = 结算不含税 + 结算税额`，则 `结算销售额差异 = 结算不含税金额差异 + 结算税额差异`。


### 6.7 要「写某张表 / 生成某类单据」前，先找这张表的既有使用者 —— 能照抄就别自造

接到"把结果写入 XX 表""生成 XX 单据"的需求时，**不要先设计一套新机制**。先在**整个工作区**（不只本项目目录）搜这张表 / 这个对象名：

1. `Grep` 表名 → 列出所有引用点（谁在读、谁在写）；
2. 找到**写的那一方**，读它的写入 FORM —— 那往往就是"这个项目对这张表的**既有范式**"：编号怎么取、事务怎么提交、借贷/数量怎么校验、审计字段怎么填；
3. **优先照抄它的做法**，包括它的"土办法"（例如 `SELECT MAX(...)+1` 取号，而不是新建 `SNRO` 编号范围对象）；
4. 只照抄**与本次任务同类的部分**，并明确列出"**不照抄**什么 + 原因"（例如对方用自建类的动态工具栏，而本报表明明有静态 GUI 状态，搬过来只是多引入依赖）；
5. 顺带把对方**已有的校验**捡过来（如按 `SKB1-FSTAG` 校验科目必填的成本中心 / 利润中心、期间锁定表 `ZFIT0022`）。

> **真实教训（2026-09-18，`ZFIT0021` 差异凭证）**：设计"差异凭证写入 `ZFIT0021`"时，我先自造了 `SNRO` 编号范围、LUW 提交顺序、反向红字行冲销等一整套机制，连开 4 个待确认项，把工作量定成"中"。用户一句「**没那么复杂，参考 `ZFI_E_001`**」直接推翻 —— 那个程序读写的就是同一张表，做法只有四步：`MAX(belnr)+1` 取号、`SUM(S)-SUM(H)=0` 平衡校验、`MODIFY ... FROM TABLE` + `COMMIT WORK AND WAIT`、冲销直接 `DELETE FROM`。照抄后工作量降为"小"，阻塞项一次性全部结案。
>
> **附带必查项**：若这张表是**多程序共用**的（本例 `ZFIT0021` 同时被"管报调账"和本需求写入），必须评估互相影响 —— 我们的记录会出现在对方列表里、也可能被对方按勾选误删 → 用一个固定标识（如 `SGTXT` 前缀）作区分，并写进风险表与上线说明。

### 7. 不要臆断下游影响

计算结果若可能进入凭证/接口/下游单据，必须单开一章列方案（仅展示 / 替换原金额 / 另生成差异单据），说明各方案对已过账数据的影响，标记为待业务决策。**不要替业务选。**

## 文档结构（默认 Markdown，除非用户要求 Office 格式）

1. 文档信息表（程序、需求来源、关联对象、目标环境、状态）
2. 需求概述（原文要点 + 表格化）
3. 术语与口径定义（**把"90 表示 90% 还是 0.90"这类写成表**）
4. 现状分析（相关表结构、既有程序能力、目标程序现有计算的行号定位、字段链路证据、可配置性缺口）
5. 详细设计（总体流程、取数设计、计算设计、数据结构变更、列变更、影响核对表）
6. 边界与异常处理（空值、负值、无配置、数据损坏、SQL 异常逐条给处理方式）
7. 下游影响（凭证/接口）
8. 权限、性能与传输（含上线顺序）
9. 测试用例（匹配类 + 计算类 + 回归类，编号 T01…）
10. 待确认问题清单（**P0 阻塞 / P1 / P2 分级**，每条给建议方案）
11. 影响与风险分析 + 需求文档与代码的差异对照表
12. 工作量拆分

## 语言与格式

- 中文，注释/表格优先；行号引用写成 `文件:行号` 形式，方便评审跳转。
- 伪代码用 ABAP 语法书写，中文注释写在被注释代码上方（与项目惯例一致）。
- 待确认项必须给出**具体到可回答的问题**，例如"订单单价 10 元、折让率 90 时，结算单价应为 9.00 还是 1.00"，而不是"请确认折让率口径"。

## 交付

完成后调用 present_files 展示文档，并在回复里点出最值得注意的 2–3 个发现（尤其是类型不一致、参考表错误、需求前提不成立这类会埋坑的问题）。

### 交付物清单（按需）

一次完整的改造交付通常包括三样，缺一样对方就做不下去：

1. **开发文档**（本 Skill 的主产物）
2. **改造后的源码**：在**源文件上就地修改**，同时把改造前内容另存一份备份文件（命名如 `<程序名>_改造前备份.txt`），并在文档里写明回滚方法。写入用**字节级操作**保留原编码与换行（Mass Download 导出多为 GBK/ANSI + CRLF），写盘后校验「文件字节 == 预期内容」。
3. **前置对象的 GUI 操作步骤**：DDIC 对象（数据元素、表字段）不是代码，必须有人在 SAP GUI 里建。**只要用户不是资深开发、或说自己是新手，就要单独写一份操作手册**，粒度到"点哪个按钮、填哪个页签、按哪个快捷键"，并附常见报错对照表。

### 操作手册的写法要点

- 每步给：事务码 → 页签/单选按钮 → 输入值 → 按钮名（中文 + 英文，GUI 语言不定）→ 快捷键。
- **明确标出"只在开发机(DEV)改"**，以及数据元素必须先激活才能被表引用。
- **查开发包的方法**给一个可自证的：`SE16 → TADIR → OBJECT='TABL' + OBJ_NAME='<表名>' → DEVCLASS`。
- 传输请求怎么填（包 → 创建对象目录条目 → 创建/复用请求）要说清楚，并提醒所有对象放同一个请求。
- **危险动作必须显式警告**：会真实产生业务数据的按钮（生成凭证、过账、删除）要写"第一次测试不要点"，并说明应该在哪个环境测。
- 能省的步骤就省：新建数据元素时优先**复用系统里已有的数据元素**（如折让率复用配置模块的 `ZFI_SDISC_RATE`），既少建对象又天然保证口径一致。建金额类数据元素时优先挂已有域，比手填预定义类型少出错。
- **DDIC 必填项要提前写进手册，不要等对方踩坑**：
  - 给表加 `CURR` / `QUAN` 字段时，SE11 里**必须同时填「参考表 + 参考字段」**（小数位由货币/计量单位决定），漏了激活会报 `指定参考表和参数字段`。手册要给出"照抄同表已有同类字段"的做法，而不是让他猜。
  - 加字段激活后，日志里通常还跟着几条黄色警告（`缺少用于表的增强类别`、`键值长度 > 120`）。要明确写清**黄色不阻止激活、红色才是根因**，否则对方会去追一堆无害的警告。
  - 激活失败时日志可能出现「字段级别上结构更改（DB 被调整）」，意味着数据库可能只调整了一部分 → 提醒修好后**重新激活**，必要时 `SE14` 调整数据库。
- **教对方读日志比解释报错本身更有价值**：SAP 的激活日志用红/黄/绿三色分级，且最后一行往往是"检查导致错误"这类汇总行。手册里应有一句"只处理红色那几行，按上面的红行定位根因"。
- **ALV 报表新增列时，必须提前交代"布局"问题**：`i_save = 'A'` 的报表会按用户保存过的布局显示，**老用户的布局里没有新列，新列就不会出现**，而且他们看到的结果与开发/测试环境不一致，极易被当成"功能没上线"。
  - 一步诊断法写进手册：打开 ALV 的「布局」对话框看列清单里有没有新列 —— **有**说明程序已是新版、只是布局没显示；**没有**说明程序还是旧版本。这一步能一次区分两类原因，避免误改代码。
  - 上线说明里必须带上"让用户切标准布局 / 删除个人布局"这一步。这与代码无关，但不写就会被反复追问。
- 收尾章：释放传输请求（先释放任务再释放请求）、回滚步骤、"还没做完的部分"。
- 最后放一页 `事务码速查`，方便对方打印对照。
